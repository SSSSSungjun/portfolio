PROJECT 01 · ANDROID / BACKEND

Bike - book

사내 공용 자전거의 신청·승인·이용·반납 흐름을 관리하는 서비스

ROLEAndroid & Backend기술 설계 및 구현
MAIN UI / FLOW대표 화면 또는 서비스 흐름 이미지

WHY THIS PROJECT

실제 사용 환경에서는 정상 요청보다 실패 상황이 더 중요했습니다.

네트워크 단절, 같은 시간대 예약, 재전송에 따른 중복 요청, 사용자별 권한까지 함께 고려해야 했습니다.

Kotlin · Compose · Room · WorkManager · Ktor · Spring Boot · PostgreSQL

DESIGN DECISION

네트워크 성공 여부만으로 사용자 작업의 완료를 판단하지 않았습니다.

Room을 앱의 로컬 단일 소스로 두고, 네트워크가 끊겨도 반납 상태를 보존한 뒤 WorkManager가 재전송하도록 구성했습니다.

WHY

사용자는 네트워크 상태와 무관하게 자신의 작업이 보존되길 기대합니다.

UI가 원격 응답에 직접 의존하지 않게 하면 화면 상태와 재시도 흐름을 분리할 수 있고, 실패 후 복구도 일관되게 다룰 수 있습니다.

EFFECT

오프라인 상황에서도 작업을 잃지 않는 흐름

반납 요청을 다시 시도할 수 있고, 로컬 상태를 기준으로 UI를 유지해 사용자 경험의 단절을 줄였습니다.

CODE EXCERPTRoom + WorkManager 재전송 흐름실제 프로젝트 코드 스니펫 추가 예정

MORE DECISIONS

  • PostgreSQL exclusion constraint로 시간대 예약 충돌을 DB에서도 방어
  • UUID idempotency key와 advisory lock으로 중복 요청 처리
  • JWT·Refresh Token rotation과 서버 측 역할·소유권 검증
  • Repository 인터페이스와 Fake/Ktor RemoteDataSource 분리로 교체 가능성 확보
RESULT사내 실제 사용 가능성 검토 단계까지 진행

운영 환경과 보안 기준을 개발 과정에서 직접 마주한 프로젝트입니다.

PROJECT 02 · BACKEND / FRONTEND

대나무숲

로그인 없이 사용하는 사내 익명 게시판

ROLEFull StackBackend 중심 설계 및 구현

CORE QUESTION

익명 서비스라고 해서 권한과 정합성까지 익명일 수는 없었습니다.

사용자에게 로그인 절차는 없애되 작성자 소유권과 동시 요청의 데이터 정합성은 서버가 책임지도록 설계했습니다.

Spring Boot · JPA · PostgreSQL · React · TypeScript · k6
WEB UI / LOAD TEST게시판 화면 또는 부하 테스트 결과 이미지

DESIGN DECISION

작성자 여부를 프론트 값이 아니라 서버 세션으로 확인했습니다.

쿠키 기반 익명 세션을 사용하고 수정·삭제 시 서버가 소유권을 다시 검증하도록 했습니다.

CONCURRENCY

동시에 요청돼도 결과가 우연에 맡겨지지 않도록 했습니다.

조회수는 원자적 UPDATE, 수정·좋아요에는 비관적 잠금과 unique constraint를 적용했습니다.

EFFECT

권한과 데이터 정합성을 서버가 끝까지 보장

사용 편의성을 위해 인증 UI를 줄이면서도 작성자 검증과 중복 데이터 방지는 유지했습니다.

PROJECT 03 · ANDROID

Mori

EC2 서버의 CPU·메모리·디스크·네트워크 상태를 조회하고 시각화하는 Android 앱

ROLEAndroid단독 구현
DASHBOARD / CUSTOM CHART서버 지표 대시보드 화면

STRUCTURE

화면이 데이터 획득 방식에 직접 묶이지 않게 했습니다.

feature·core·data 기준으로 모듈을 나누고 화면과 데이터 계층의 책임을 분리했습니다.

DATA FLOW

서로 독립적인 지표 요청은 기다리지 않고 함께 가져왔습니다.

Coroutines async/await로 여러 서버 지표 API를 병렬 조회해 대시보드 데이터를 구성했습니다.

EFFECT

화면 구조와 데이터 소스를 독립적으로 변경할 수 있는 기반

데이터 획득 방식이 바뀌어도 UI 수정 범위를 줄이고, 여러 지표를 한 화면에서 빠르게 보여줄 수 있게 했습니다.

PROJECT 04 · ANDROID

관:상견례

사용자 매칭과 실시간 1:1 채팅을 제공하는 Android 앱

ROLEAndroid앱 개발
CHAT / MATCHING UI매칭·채팅 주요 화면

CORE QUESTION

실시간 메시지와 목록 데이터는 같은 방식으로 다루지 않았습니다.

즉시 도착해야 하는 채팅과 점진적으로 불러오는 목록, 앱 재실행 후에도 남아야 하는 사용자 상태를 각 특성에 맞게 분리했습니다.

Kotlin · Compose · WebSocket · OkHttp · DataStore · Paging3

REALTIME

채팅은 WebSocket으로 연결 상태와 메시지 흐름을 관리했습니다.

일반 HTTP 요청과 다른 생명주기를 가진 실시간 연결을 별도로 다루도록 구성했습니다.

STATE

목록과 로컬 사용자 상태는 각 목적에 맞는 도구를 사용했습니다.

Paging3로 목록 로딩을 나누고 DataStore로 앱 재실행 뒤에도 필요한 상태를 보존했습니다.

EFFECT

데이터 성격에 따라 상태 관리 방식을 분리

실시간 통신, 대용량 목록, 영속 상태가 서로 얽히지 않도록 책임을 나눴습니다.
